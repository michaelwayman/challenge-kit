# challenge-kit: a Claude Code plugin

## Context
challenge-kit is a reusable, **project-agnostic** Claude Code plugin that takes a coding challenge or take-home from its brief to tracked, parallel, reviewed work. It is a fresh design informed by the agent-kit runs (`~/Projects/agent-kit`, `~/P/challenge`) and fixes their problems:
- **No way to change scope.** There was no good way to add features or mark something out of scope after kickoff.
- **Scattered docs.** Scope, architecture and contracts lived in separate files.
- **Drifting copies.** Three copies of the kit diverged, and lessons learned never flowed back.

It knows nothing about any one challenge: a guided **research** step learns each project. The first target is the ConsumerAffairs WP → Django challenge, but it must work equally on unrelated projects.

## Where things live
| What | Where |
|---|---|
| Skills, agents, templates, generic working rules | the plugin, at `~/Projects/challenge-kit` (one source of truth) |
| `AGENTS.md` + `CLAUDE.md` symlink (project rules, review rules, learned rules), `SPEC.md`, `docs/research.md`, `docs/contracts/`, ADRs | the target repo, generated by kickoff and committed |
| `.claude/settings.json` (permissions, plus enabling the plugin for the project) and the `.github/` issue and PR templates and CI | the target repo, committed |

- Agents run inside the target repo, so they read its rules. Every agent prompt *explicitly* reads the root `AGENTS.md` and the nearest `AGENTS.md`, and does not rely on auto-loading.
- `/challenge-kit:eject` copies the skills and agents into the repo's `.claude/` as a visible snapshot. That is useful when graders should see the AI tooling.

## The flow
1. **`kickoff`**:
   - Reads the brief (`CHALLENGE.md` by default) and the repo, then runs **research**.
   - Drafts `SPEC.md` and asks about the gaps.
   - Proposes boundaries, contracts and tech choices, with defaults taken from the research recommendations.
   - **Final review table** of every choice, which you can edit. It includes a proposed **Priority (P0/P1/P2)** for each requirement and milestone.
   - **Ready gate:** nothing moves on until you say "ready".
   - Then it renders the repo files, opens a PR and runs `sync-github`.
2. **`research [topic…]`**:
   - Proposes an agenda of about 4–8 topics, which you edit or approve.
   - Runs one `researcher` agent per topic, in parallel.
   - Writes `docs/research.md` with evidence for each finding (file:line, command output or URL), recommendations and open questions.
   - Can be re-run per topic later.
3. **`change-spec "<add / remove / alter / move in or out of scope>"`**:
   - Applies operations on the requirements, out-of-scope items, tech choices and boundaries.
   - Offers a research pass if it needs knowledge.
   - Shows an impact table: issues, PRs, contracts and milestones.
   - **After you confirm:** edits `SPEC.md` with a changelog entry, then runs `sync-github` (creates, edits, re-plans and closes issues, and comments on PRs), and opens a SPEC PR.
4. **`sync-github`** (idempotent):
   - Reconciles `SPEC.md` with labels (`ready`, `blocked`, `plan-approved`, `needs-triage`, `contract`, `integration`, `service:<s>`, `req:R<n>`), milestones, branch protection and issues. Each issue carries a hidden `ck:` marker, so a re-run updates it instead of duplicating it.
   - **Sets up one GitHub Project (v2) per repo as the control panel:**
     - Created once, linked to the repo, with its number stored in `SPEC.md`.
     - Fields: **Status** (Todo / Ready / In progress / In review / Done) and **Priority** (P0 / P1 / P2).
     - A board view (the API cannot set grouping; "Group by → Milestone" is one click in the board).
     - Every issue is added to it.
     - Needs the `project` scope once: `gh auth refresh -s project`. The skill checks for it and tells you if it's missing.
   - Shows the diff and applies it only after your confirmation, reopening milestones as needed.
   - **You choose the order with Priority:**
     - Kickoff proposes a priority for each R or issue as a column in the final review table; you edit it before "ready".
     - change-spec proposes priorities for new or changed work in its impact table.
     - After that, change Priority in the Project board whenever you like.
     - `sync-github` never overwrites a priority you set in the board. It only sets Priority on new items.
5. **`orchestrate [milestone…]`**:
   - **Catch up:** moves an issue from `blocked` to `ready` when its dependencies merge, and keeps the Project's Status in step (Ready, In progress when a worker starts, In review when its PR opens, Done when it merges).
   - **Pick order:**
     - Reads the Project each round and considers only issues that are `ready` with no open dependencies. A blocked issue never starts, whatever its priority.
     - Picks **P0 before P1 before P2**. Ties go to the issue that unblocks the most others, then the lowest issue number.
     - The round plan table lists issues in that order, so you can see and change it before approving.
   - **Round plan table**, one per lane, with columns Decisions, **"My reading of R<n>"** and **size budget**. You approve it, and approved issues get `plan-approved`.
   - **Lanes:** one per milestone, up to 2 workers each, each a fresh session in its own worktree.
   - **Routes questions:** how-to questions the worker decides itself; scope questions go to `change-spec`; contract changes become `contract` issues.
   - Supports **"stop / redo #n"**.
   - It never merges and never polls CI.
6. **`work-issue <n>`** (a worker):
   - Builds only `Delivers: R<n>` inside `Touches:`.
   - Runs `make check`, then a **budget check** (diff stat vs. budget; if it's well over, it stops and asks instead of opening the PR).
   - Runs `reviewer` and `contract-checker`, opens the PR ("Calls I made") with Auto-fix on, and stops.
7. **`review-pr <n>`**: run by the orchestrator when a worker reports. It runs both review agents against the real PR diff and CI status, and posts the findings as a PR comment before you review.
8. **`integrate`**:
   - Checks the contracts against the real services, plus a smoke test of the user flows the requirements name.
   - Turns those checks into `make test-integration`.
   - Files each failure as a `needs-triage` issue.
9. **`record-correction "<feedback>"`**: routes your feedback.
   - A project rule goes to the repo's `AGENTS.md`, under Learned or Review rules.
   - Feedback about the kit's own behavior becomes a proposed patch to the plugin, such as `agents/reviewer.md`.
10. **`eject`**: copies the plugin's skills and agents into the repo, and workers prefer a project copy if one exists.

**Agents** (read-only, sonnet):
- `researcher`: one topic, with evidence for each finding.
- `reviewer`: checks the diff against Decisions, `Delivers`, acceptance criteria, `Touches`, the out-of-scope items, the repo's Review and Learned rules, and the budget. **Scope creep and misreadings are findings.**
- `contract-checker`: checks the diff against `docs/contracts/`.

**SPEC.md sections**, with stable IDs that are never renumbered:
1. Requirements `R<n>` (active or removed, each with acceptance bullets and a brief § reference)
2. Out of scope `O<n>`
3. Services and boundaries
4. Contracts
5. Technology choices `T<n>`
6. Milestones `M<n>` → the `R`s each delivers
7. Changelog

## First steps
1. **Scaffold the repo:**
   - `git init ~/Projects/challenge-kit`.
   - Write `plugin.json` (name `challenge-kit`, version 0.1.0), a local `marketplace.json`, the README and `docs/design.md` (this plan).
2. **Confirm the platform details** with the claude-code-guide agent against the current docs:
   - The plugin manifest and the skill and agent frontmatter.
   - `${CLAUDE_PLUGIN_ROOT}`.
   - Whether subagents auto-load `CLAUDE.md`.
   - Whether a plugin can ship permissions (if not, kickoff renders `.claude/settings.json`).
   - How a project's settings enable a plugin.
   - The `--plugin-dir` dev loop.
   - The validate command.
3. **Write the foundations:** `templates/`, `rules/working-rules.md` (generic rules carried from `~/P/challenge/AGENTS.md`) and `scripts/gh-bootstrap.sh`.
4. **Build research first:** the `researcher` agent, then the `research` skill. Try it on a local clone of the CA challenge via `--plugin-dir`.
5. **Then the rest, in order:** sync-github → kickoff → change-spec → work-issue + reviewer + contract-checker → orchestrate → review-pr → integrate → record-correction → eject. Use superpowers:writing-skills, and keep each SKILL.md short.

## Addendum: time box, grade, replan and bundle (2026-10-26)
Kickoff now takes a wall-clock time box, a grade (demo / solid / production), research and contract depth, and a delivery shape, recorded in SPEC.md's "Time box and grade" section. `rules/grades.md` is the single definition the skills read: what each grade builds, tests and reviews; S/M/L estimates with a grade multiplier and a calibration factor; the reserve; and the speed levers. Kickoff's fit check and the orchestrator's clock check offer process levers (planning, per-ticket effort, parallelism) before grade, and grade before scope; the user picks every change. `replan` changes time, grade or speed for the project or, as overrides, for chosen Rs. `bundle` links planned issues as sub-issues of one bundle issue built in one PR, one per service by default; crossing a service boundary needs the user's explicit yes. Time is logged on a pinned Progress log issue, so nothing is pushed to main for logging.

## Addendum: issue size (2026-10-27)
The ck-dryrun run created 36 issues at kickoff (one per service and layer), then bundled 27 of them back into 6 issues to ship them. sync-github now creates **one issue per service per milestone** by default, with the pieces as a checklist inside, so issues match how work is actually built and reviewed. Kickoff's former "Delivery" question is now **Issue size**: per milestone (default) or fine, recorded in SPEC.md. Fine keeps the old behaviour, and `bundle` applies only to it.

## Addendum: report (2026-10-27)
Bugs in merged work had no route: filing by hand meant getting labels and milestones right, and asking the orchestrator made the issue `needs-triage`, so the user triaged their own report. `report` takes a plain-words bug or small fix, sends anything beyond an R's acceptance to change-spec, and otherwise files one issue per service from the task template, already triaged (`ready` or `blocked`, `service:` and `req:` labels, milestone reopened if needed, on the Project), after the user confirms the draft. Its `ck:report:` marker keeps sync-github from rewriting it.

## Addendum: visual design for UI deliverables (2026-10-27)
In ck-dryrun, `<BrandList />` met every acceptance bullet and still looked plain: research covered how it was built, not how it should look, no R set a visual bar, and no step looked at the rendered UI. Now every user-facing UI deliverable gets a visual design topic in research that ends in checkable bullets; kickoff copies them into the R as `Visual:` acceptance; M1 adds a `make screenshots` target; the worker captures and self-checks screenshots at 375px and 1280px, and the reviewer reads them and judges each bullet. Depth per grade is in `rules/grades.md` (UI checks).
